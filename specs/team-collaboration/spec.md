# MewCode 长期团队协作 Spec

## 背景

MewCode 已支持主 Agent 将独立子任务委派给短生命周期子 Agent，并提供后台运行、任务状态跟踪、权限隔离以及基于 Git worktree 的写入隔离。这套能力适合一次性委派，但子 Agent 之间没有共同的团队身份、共享任务清单或点对点通信渠道；任务结束后也不能作为同一名成员带着既有上下文接受后续指派。复杂目标仍需要主 Agent 充当所有信息的中转站，难以持续组织多个成员并行协作。

本功能把显式绑定团队的主 Agent 升级为 Team Lead，引入可跨 CLI 重启保留的长期团队。团队成员可围绕共享任务与邮箱直接协作，Lead 负责拆解目标、控制依赖与审批、组织并行工作以及原子集成成员成果。运行进程不跨 CLI 退出存活；成员停止或进程重启后，通过持久化上下文和未读消息恢复，而不依赖后台守护进程。

## 目标

- 提供可创建、恢复、切换和保护性归档的长期团队，并持久记录团队负责人、成员花名册、工作位置与生命周期状态。
- 让团队成员以稳定身份长期存在，保留规范化上下文，在空闲或 CLI 重启后可被消息唤醒并继续接受任务。
- 支持强隔离与轻量两类成员运行后端，根据环境优先选择，并向 Lead 明示实际选择及任何降级原因。
- 提供团队专属的共享任务和邮箱能力，使成员无需经过 Lead 中转即可读取工作状态、创建协作事项及点对点或广播沟通。
- 让 Lead 把用户目标拆为带依赖的共享任务，指派成员并跟踪阻塞、完成和空闲状态。
- 对要求审批的成员实施按成员、任务和计划版本绑定的开工审批，同时保留既有高风险操作权限检查。
- 让 Lead 在成员工作全部就绪后，以不破坏 Lead 原分支的方式集成和验证各成员成果；无法处理的冲突应中止集成并明确上报。
- 提供双重启用的 coordinator 模式，使 Lead 专注于派工、决策、消息、终止和代码集成，并从能力层面阻止其直接修改源码。
- 保持普通主入口、普通一次性子 Agent 以及现有委派、权限、会话和 worktree 行为兼容。

## 功能需求

### 团队与成员生命周期

- F1：用户必须显式创建或恢复一个团队，当前主会话才绑定为该团队的 Lead 并获得 Lead 侧团队能力。一个主会话同一时间最多绑定一个团队，用户可持久化多个不同名称的团队并在其间显式切换。
- F2：团队必须具有稳定且唯一的名称，并持久记录负责人、状态、成员花名册及持久化位置。成员条目必须记录团队内唯一名称、角色快照、工作目录、实际运行后端、是否需要 Lead 审批和当前生命周期状态。
- F3：团队数据必须位于用户目录下按团队名称区分的独立目录中，并包含恢复团队所需的元数据、共享任务、成员邮箱、成员上下文和审计信息。团队目录不得写入项目仓库。
- F4：团队创建仅支持有效 Git 工作区。可写成员必须始终使用独立 worktree 和长期分支，包括使用同进程轻量后端时；只读成员可以共享只读工作区。
- F5：创建成员时必须引用一个已加载的现有 Agent 角色，并为其指定团队内名称、后端偏好和是否需要审批。成员固定使用创建时的角色快照；角色定义热更新不改变既有成员，Lead 可显式将成员升级到当前有效角色版本。
- F6：团队存续期间必须保留成员的长期 worktree 和分支。一次成功集成后，系统必须在确认成员工作区安全的前提下将其同步到新的 Lead 基线，再将成员标记为空闲，以便继续在同一工作目录接受任务。
- F7：空闲成员收到新的有效消息或任务后，必须使用其持久化上下文恢复运行，而不是创建新的成员身份。恢复时先接收停止期间积累的新消息，再开始新的模型轮次。
- F8：系统必须持久化成员的规范化对话历史、角色与运行元数据、当前任务、审批状态和邮箱读取位置；不得恢复临时权限授权、在途工具调用或进程内部运行状态。
- F9：CLI 正常退出时必须有界停止团队成员并持久化可恢复状态，不得要求成员进程在 CLI 退出后继续存活。再次启动后可恢复团队、成员、任务和未读消息，但不得把中断的工具调用当作已完成或原地续跑。
- F10：归档团队前必须停止成员并冻结新任务。存在运行中任务、未合并提交、未提交改动或未处理审批时必须拒绝归档并列明原因；状态干净后清理成员运行资源并保留不可重新激活的归档数据以供审计。

### 成员运行后端

- F11：成员必须支持强隔离后端和同进程轻量后端。强隔离后端在独立终端窗格中运行完整成员实例；轻量后端在当前进程内独立运行，二者必须遵守相同的成员身份、任务、邮箱、审批、权限和 worktree 边界。
- F12：成员可显式选择支持的后端或选择自动模式。自动模式必须优先选择环境中可用的强隔离后端，再选择同进程轻量后端；每次创建或恢复都必须向 Lead 报告实际后端。
- F13：自动模式从优先后端降级时必须明确报告不可用原因和最终选择，禁止静默降级。显式指定的后端不可用时必须创建失败，不得自动替换为其他后端。
- F14：后端探测、启动、唤醒或退出失败只能影响对应成员，并向 Lead 提供可定位的状态；不得导致团队元数据、其他成员或主会话崩溃。

### 工具可见性与能力边界

- F15：未绑定团队的普通主入口和普通一次性子 Agent 不得看到任何团队专属协作工具。绑定团队的 Lead 只能看到 Lead 侧能力；团队成员只能看到成员侧共享任务和邮箱能力，不得看到团队创建、归档、成员管理或代码集成能力。
- F16：Lead 必须能够创建、恢复、切换和归档团队，添加、升级、停止和恢复成员，指派或取消任务，发送消息，以及启动结果集成。成员不得通过自身协作工具提升权限或改变团队归属。
- F17：所有团队专属操作都必须校验当前会话或成员的团队身份、角色和目标范围；不得访问或修改其他团队的数据，也不得通过伪造名称读取其他成员的私有上下文。

### 共享任务

- F18：每个团队必须维护一个可持久化的共享任务清单。任务至少应具有稳定 ID、标题、说明、状态、负责人、依赖任务、创建者、创建与更新时间、工作记录和逻辑删除状态。
- F19：任务依赖仅允许引用同一团队内尚未逻辑删除的任务，并表示所有依赖完成后该任务才可开始。系统必须拒绝不存在的依赖、自依赖以及直接或间接依赖环，并可明确查询任务是否就绪及未满足的依赖。
- F20：本阶段任务状态必须至少区分待处理、被依赖阻塞、等待审批、可开始、进行中、已阻塞、已完成和已取消；状态变化必须保留可追溯记录，且完成或取消后的非法倒退必须被拒绝。
- F21：Lead 可创建和读取所有任务，并独占任务指派、依赖变更、取消和逻辑删除权限。成员可读取团队全部任务、创建新任务，并更新自己负责任务的状态与工作记录；成员需要改派或调整依赖时必须向 Lead 发消息请求。
- F22：成员不得在依赖未完成、任务未指派给自己或所需计划尚未获批时开始任务。系统必须返回可定位的阻塞原因，而不是仅依赖提示约束。
- F23：删除任务采用逻辑删除。只有未开始或已经结束的任务可删除，运行中任务必须先取消；存在其他未删除任务依赖它时必须拒绝删除。默认查询隐藏已删除任务，但其历史、消息引用和审计记录必须仍可追溯。
- F24：共享任务的并发增删查改必须保持一致；冲突更新不得静默覆盖较新的状态，单个写入失败不得留下部分任务内容。

### 注册表、邮箱与消息协议

- F25：点对点通信必须先通过团队名称注册表解析目标成员，再把消息写入目标成员的独立邮箱。名称不存在、已归档、重复或属于其他团队时必须拒绝投递，并提供不泄露其他团队信息的错误。
- F26：每条落盘消息必须包含发件人、正文、时间戳、已读状态和摘要。写入时由系统补充可信时间戳、默认标记为未读并生成有界摘要；读取或确认后必须持久更新已读状态。
- F27：成员与 Lead 必须能够发送自由文本点对点消息；有权限的发送者也可广播给团队内所有其他活动成员。广播必须为每个收件人产生独立可读状态，并报告逐个投递结果，部分失败不得撤销已成功投递的消息。
- F28：本阶段必须支持四类结构化协议消息：任务指派或变更、计划审批请求、计划批准或驳回、任务状态通知。结构化消息必须校验必需字段和引用对象；普通讨论、代码审查与合并协商继续使用自由文本。
- F29：邮箱写入成功后，运行中的目标必须得到新消息通知；强隔离后端还必须额外唤醒对应终端窗格。目标当前空闲或进程已退出时，消息继续持久化并在下次恢复时优先注入，不得因无法即时唤醒而丢失。
- F30：同一条消息不得因重试、恢复或重复唤醒而被成员重复处理；消息写入、读取位置和已读状态在并发访问或进程异常时必须保持可恢复。

### 计划审批

- F31：标记为需要审批的成员在每个任务开工前，必须向 Lead 发送包含成员、任务和计划版本的结构化审批请求，并进入等待审批状态；未获得有效批准前不得执行计划中的写入或副作用操作。
- F32：Lead 必须使用唯一且可机器校验的结构化回复批准或驳回计划。审批决定必须绑定成员、任务和计划版本；任一绑定项不匹配、决定已撤销或计划内容发生变化时，原批准失效并要求重新审批。
- F33：批准只允许成员执行对应版本计划，不得绕过现有工具权限、沙箱或高风险操作审批。驳回必须携带原因，成员可据此修订计划并提交新版本。
- F34：审批请求、决定、失效和重新申请必须持久化并可审计；成员或 CLI 恢复后必须延续实际审批状态，不得把待审批计划误判为已批准。

### Lead 编排与代码集成

- F35：Lead 必须能够把用户目标拆为共享任务、声明依赖、指派成员并启动所有已就绪任务；无依赖或依赖已满足的任务可并行运行，依赖未满足的任务保持阻塞。
- F36：成员自然完成当前工作后必须提交任务状态通知，持久化最终工作记录，将自身标记为空闲并通知 Lead。任务失败、被取消或无法继续时也必须发送相应状态与可定位原因，不得伪装为完成。
- F37：Lead 只有在待集成任务均完成且相关成员工作区满足集成前置条件时，才能启动代码集成。集成顺序必须尊重任务依赖关系，并能识别各成员尚未集成的成果。
- F38：多个成员成果必须先合入临时集成分支并运行约定验证；只有全部合并和验证成功后，才可将 Lead 分支推进到集成结果。集成期间不得直接改写原 Lead 分支。
- F39：发生冲突时，Lead 可读取和诊断冲突，并优先把可修复事项派给适当成员处理后重新集成；Lead 不得亲自编辑冲突源码。若冲突或验证失败最终无法解决，必须中止并丢弃本次临时集成结果、保留原 Lead 分支并向用户上报证据。
- F40：成功集成后必须记录纳入的成员成果、验证结果和新基线，再安全同步相关长期成员分支；失败集成不得把部分结果标记为已纳入，也不得静默丢弃成员原始成果。

### Coordinator 模式

- F41：coordinator 模式只有在应用配置中的能力开关已开启，且用户在当前运行环境中主动设置专用环境变量时才生效；任一开关缺失都必须保持普通 Lead 模式并明确报告原因。
- F42：coordinator 模式生效后，Lead 必须失去直接创建、修改、删除或移动工作区文件的能力，仅保留读取、团队编排、成员终止、消息和代码集成所需能力。
- F43：coordinator 模式保留的 shell 必须限制为只读检查和 Git 集成操作，可查看状态、差异与冲突，并执行临时分支集成、验证、暂存及提交集成结果；不得通过 shell、脚本、重定向或子进程绕过限制修改源码。
- F44：coordinator 模式下需要源码或冲突内容修改时，Lead 必须创建或更新共享任务并委派给成员。模式切换和被拒绝的写入尝试必须可观察且可审计。

## 非功能需求

- N1：团队元数据、共享任务、邮箱、审批和成员上下文的持久化更新必须具备进程内并发安全和崩溃可恢复性；不得向读取者暴露半条消息、半个任务或相互矛盾的状态组合。
- N2：团队名称、成员名称、任务 ID、消息 ID、计划版本和集成记录必须在各自作用域内稳定且唯一；恢复、重试和重复请求不得创建无法区分的副本。
- N3：同一任务只能发生一次有效的终态转换，同一消息最多被同一收件人消费一次，同一计划决定只能作用于精确匹配的版本，同一成员成果不得在一次集成中重复纳入。
- N4：团队、成员、任务、邮箱和 worktree 必须严格限制在所属团队与工作区边界内。路径解析必须防止目录穿越、符号链接逃逸、名称碰撞以及通过持久化内容访问团队目录之外的数据。
- N5：成员身份、发件人、审批人、任务负责人和 Lead 身份必须来自可信运行上下文，不得接受模型通过普通参数自行声明或冒充。结构化消息中的身份字段必须与调用者身份一致。
- N6：持久化内容和诊断不得记录 API 密钥、临时授权、完整敏感工具参数或其他凭据。成员上下文若包含现有敏感信息，必须继续遵守项目既有的脱敏、外置和权限边界。
- N7：后端差异不得改变业务语义、成员权限或持久化格式。相同任务在强隔离和轻量后端下必须遵循同一状态机、审批规则、消息协议和 Git 隔离要求。
- N8：后端自动选择必须确定、可解释且可测试。能力探测结果、选择顺序、降级理由、启动失败和唤醒失败必须以有界诊断呈现，不得泄露环境凭据或完整进程参数。
- N9：成员并发数、单团队成员数、任务数量、依赖数量、邮箱消息大小、消息摘要大小、上下文大小、广播收件人数、恢复与停止等待时间都必须具有配置或实现硬上限，禁止无界占用内存、磁盘、终端窗格或线程。
- N10：成员上下文和消息注入必须遵守现有上下文预算、外置与摘要机制；超大历史或邮箱积压不得导致无界 Provider 请求，也不得在截断时丢失未处理状态。
- N11：成员启动、停止、恢复、消息通知、终端唤醒和集成操作必须具有有界等待与取消能力。单个成员、窗格或 Git 子进程卡住不得无限阻塞 Lead、CLI 退出或其他成员。
- N12：单个团队文件损坏、成员异常退出、邮箱投递失败、终端唤醒失败、角色升级失败、Git 操作失败或审计写入失败不得导致其他团队、其他成员或普通主会话崩溃；系统必须保守停止受影响操作并给出可定位错误。
- N13：所有任务与审批状态转换、消息投递与读取、成员后端选择与生命周期变化、coordinator 模式判定、写入拒绝、团队归档和代码集成结果都必须产生有界、可关联且不含敏感内容的审计记录。
- N14：系统必须能在恢复时检测持久化版本不兼容、缺失文件和不一致状态；不得猜测性修复会改变任务、审批、消息已读状态或 Git 成果的关键数据。
- N15：代码集成必须具备原子可见性和幂等保护。失败或取消不能推进 Lead 分支，重试必须能区分已集成与待集成成果，并保留足够证据定位冲突与验证失败。
- N16：coordinator 模式的写入限制必须由工具注册、权限和命令执行边界共同强制，不能只依赖系统提示。等价的别名、脚本、重定向、管道、子进程和 Git 外部驱动不得成为绕过路径。
- N17：团队专属工具的名称、参数结构和返回结构在团队状态、成员数量、后端选择、coordinator 模式和角色热更新期间必须保持稳定；工具可见性可按可信身份切换，但不得把无权工具先暴露再仅靠运行时拒绝。
- N18：新增能力必须兼容现有普通 Agent Loop、一次性子 Agent、后台任务、Skills、Hooks、MCP、权限、会话恢复、上下文管理、Plan/Do 模式、命令路由和 worktree 隔离行为。
- N19：实现必须支持项目当前声明的 Python 3.10 及以上版本，并通过确定性单元、集成和端到端测试覆盖并发更新、进程恢复、后端降级、审批竞争、消息幂等和原子集成。
- N20：本阶段产生的用户可见状态、错误和审计摘要必须清楚区分团队、成员、任务、消息、审批、后端和集成对象，使用户无需查看内部文件即可判断下一步行动。

## 不做的事

- 不实现跨机器、跨用户主目录或跨共享文件系统的分布式团队；一个团队只在创建它的本机和用户环境中恢复。
- 不实现成员间 Token 级或事件级实时流式通信、共享实时对话窗口或远程屏幕控制；本阶段通信边界是持久化消息和显式唤醒。
- 不提供在 CLI 退出后继续运行成员的守护进程、系统服务或远程执行器，也不承诺恢复中断中的工具调用。
- 不实现多级组织结构、子团队、共同 Lead、动态 Lead 选举、成员创建孙成员或一个成员同时加入多个活动团队。
- 不实现复杂任务调度约束，例如资源配额、优先级抢占、截止时间、条件分支、动态关键路径、部分依赖满足即可开始或跨团队依赖。
- 不实现自动理解用户目标即可创建完整团队的无监督编排；Lead 仍负责提出并执行可观察的任务拆解、指派和依赖决策。
- 不新增计划批准以外的权限绕过机制；Lead 的团队审批不能代替现有工具权限、沙箱和用户高风险操作审批。
- 不把代码审查、合并请求和合并结果定义为新的结构化消息协议；本阶段通过自由文本、任务状态和代码集成记录表达。
- 不开放普通一次性子 Agent 使用共享任务、邮箱或成员管理工具，也不把现有 `Agent`/`Task` 一次性委派对象自动升级为团队成员。
- 不为成员引入团队专属的自由文本角色定义语言；成员复用现有 Agent 角色目录及其快照语义。
- 不支持非 Git 工作区的可写团队协作，也不通过共享写目录或完整目录复制来替代成员 worktree。
- 不为每个任务创建并销毁成员身份或 worktree；本阶段成员、worktree 和分支在活动团队生命周期内长期保留。
- 不实现任意第三方终端、远程终端或 IDE 的通用分屏自动化；只支持技术设计阶段明确列出的可探测后端，其他环境使用显式失败或已声明的轻量降级。
- 不自动解决需要修改源码的 Git 冲突，不允许 coordinator 模式下的 Lead 以任何方式直接编辑冲突文件；修复必须委派给成员。
- 不在集成验证失败后保留部分成员成果到 Lead 分支，也不采用逐次回滚来模拟原子集成。
- 不支持归档团队重新激活、带未合并工作强制归档或静默丢弃团队目录、邮箱、任务历史和审批审计。
- 不实现任意历史版本迁移或猜测性修复损坏的团队数据；仅支持技术设计中明确版本的兼容读取或显式迁移。
- 不新增可由模型自行切换的 coordinator 模式；能力开关和用户环境变量任一缺失时都不得启用。
- 不承诺终端窗格后端与同进程后端具有相同的进程级安全强度；只保证两者具有相同的业务、权限、持久化和 Git 写入边界。
- 不改变现有普通会话、Skills、Hooks、MCP、一次性子 Agent 和后台任务的持久化或恢复语义，除非为稳定接入团队能力所必需且已在本 Spec 中明确。

## 验收标准

### 团队、成员与后端

- AC1：未绑定团队的主会话不显示团队专属工具；显式创建或恢复团队后，当前主会话成为该团队 Lead 并显示稳定的 Lead 工具集合。切换到另一团队时旧绑定失效，同一会话不能同时操作两个团队，而用户目录中可独立恢复多个团队。（覆盖 F1、F15、F17、N17）
- AC2：在有效 Git 工作区创建团队后，用户团队根目录下出现按规范化团队名隔离的数据目录，能读取稳定团队名称、负责人、状态、成员花名册和持久化位置；同名活动团队、非法名称、非 Git 工作区或会逃逸根目录的名称均被结构化拒绝且不留下部分目录。（覆盖 F2、F3、F4、N2、N4）
- AC3：添加可写成员后，其花名册条目包含团队内唯一名称、角色快照标识、独立 worktree、长期分支、实际后端、审批要求和生命周期状态；只读成员可使用受限共享工作区，但无法通过其工具或 shell 写入。重复成员名或无效角色不创建成员。（覆盖 F2、F4）
- AC4：成员只能引用当前有效的现有 Agent 角色。角色文件之后发生热更新时，既有成员继续使用旧快照；Lead 显式升级后，新快照仅在校验成功时原子替换，失败时成员仍保留原快照和可恢复状态。（覆盖 F5、N12）
- AC5：成员完成一次任务并成功集成后，原 worktree 和长期分支仍存在，分支安全同步到新的 Lead 基线，成员转为空闲；后续任务恢复同一成员身份和工作目录，而不是创建新 worktree 或新成员。（覆盖 F6）
- AC6：空闲成员收到新任务或消息后，从持久化的规范化对话、角色和运行元数据、当前任务、审批状态及邮箱读取位置恢复，先注入停机期间的未处理消息，再发起新模型轮次；临时权限、进程对象和中断中的工具调用均未恢复。（覆盖 F7、F8）
- AC7：CLI 正常退出能在配置的期限内停止成员并保存可恢复状态；重新启动后团队、成员、任务、审批和未读消息恢复，但退出前在途工具调用不会被标记完成或从调用中点续跑。卡住的成员不会使退出无限等待。（覆盖 F9、N11）
- AC8：归档请求会先冻结新任务并停止活动成员。存在运行任务、待审批、未提交改动或未合并提交时，归档被拒绝并逐项列出原因；状态干净时才清理成员运行资源并把团队转为只读归档，审计数据仍可查看且无法恢复为活动团队。（覆盖 F10）
- AC9：同一成员角色分别使用强隔离后端和轻量后端运行时，均遵守相同身份、任务状态、消息、审批、权限和独立 worktree 规则；强隔离实例运行在独立终端窗格，轻量实例运行在当前进程内。（覆盖 F11、N7）
- AC10：自动后端模式在强隔离能力可用时选择强隔离并报告实际后端；强隔离不可用时选择轻量后端，同时报告探测失败原因和降级结果。显式指定不可用后端时创建失败，不发生替换。（覆盖 F12、F13、N8）
- AC11：模拟单个成员的后端探测、启动、唤醒和停止失败时，该成员进入可定位的失败或离线状态，Lead 收到有界诊断；团队元数据、主会话和其他成员继续可用。（覆盖 F14、N8、N12）

### 工具与共享任务

- AC12：工具清单快照显示：普通主入口和普通一次性子 Agent 没有团队工具；Lead 只有团队管理、Lead 侧任务、消息和集成工具；成员只有成员侧任务与邮箱工具。角色热更新、成员数量和任务状态变化不改变各工具名称、参数及返回结构。（覆盖 F15、N17）
- AC13：Lead 可执行团队和成员生命周期、任务调度、消息及集成操作；成员尝试创建或归档团队、管理成员、集成代码、改变团队归属或访问其他团队时，在数据访问前被拒绝。伪造团队名、成员名或发送者字段不能提升权限或读取私有上下文。（覆盖 F16、F17、N5）
- AC14：新建任务后，共享清单可读取其稳定 ID、标题、说明、状态、负责人、依赖、创建者、时间、工作记录和逻辑删除状态；进程重启后字段保持一致，默认列表不泄露其他团队任务。（覆盖 F18）
- AC15：为任务设置同团队有效依赖后，查询能显示是否就绪以及全部未满足依赖；不存在、已删除、跨团队、自身或会形成直接/间接环的依赖均被拒绝，原依赖集合不变。（覆盖 F19）
- AC16：任务能按规则在待处理、依赖阻塞、等待审批、可开始、进行中、已阻塞、已完成和已取消间转换并留下历史。成员在依赖未完成、任务未指派给自己或计划未批准时请求开工，会得到具体阻塞原因且任务不进入进行中；终态非法倒退被拒绝。（覆盖 F20、F22）
- AC17：Lead 可以创建和读取所有团队任务，并可指派、修改依赖、取消和逻辑删除；成员可以读取全部团队任务、创建任务、更新自己负责项的状态和工作记录，但对他人任务或 Lead 独占字段的写入被拒绝。（覆盖 F21）
- AC18：未开始或已终结且没有存续依赖者的任务可逻辑删除，并从默认列表隐藏但仍可按审计方式读取；运行中任务、未先取消的任务或仍被未删除任务依赖的任务删除请求均失败，历史消息引用保持有效。（覆盖 F23）
- AC19：并发更新同一任务时，符合当前版本的单次更新完整提交，基于旧版本的竞争更新收到冲突而不覆盖新值；模拟写入中断后，重新读取只能看到旧完整记录或新完整记录，不会看到部分内容或相互矛盾状态。（覆盖 F24、N1、N3）

### 邮箱与结构化协议

- AC20：点对点发送先在当前团队注册表解析收件人，再写入该成员邮箱；不存在、重复、归档或其他团队名称均被拒绝，不创建孤立邮箱内容，错误也不透露其他团队成员信息。（覆盖 F25、N4）
- AC21：成功落盘的消息具有稳定唯一 ID、可信发件人、原正文、系统生成时间戳、默认未读状态和有界摘要；读取或确认后已读状态持久更新，模型参数不能伪造可信时间或发送者。（覆盖 F26、N2、N5）
- AC22：Lead 或成员可发送自由文本点对点消息；合法广播为每个其他活动收件人生成独立消息及独立已读状态，并返回逐收件人结果。模拟一个邮箱失败时，其他成功投递仍保留且失败目标可明确识别。（覆盖 F27）
- AC23：任务指派或变更、计划审批请求、计划批准或驳回、任务状态通知四类结构化消息能校验类型、必需字段、身份和引用对象并正确落盘；缺字段、错类型、无效引用或身份不匹配被结构化拒绝。自由文本仍可用于普通讨论。（覆盖 F28、N5）
- AC24：消息写入运行中轻量成员后，目标得到进程内通知；写入运行中强隔离成员后，目标邮箱持久化并触发对应窗格唤醒；目标空闲、离线或唤醒失败时消息仍保留，并在恢复时优先提供。（覆盖 F29）
- AC25：对同一消息重复投递请求、重复唤醒、并发读取或崩溃恢复后，同一收件人最多处理一次；读取位置、消息内容和已读状态保持可恢复，未处理消息不会因摘要或上下文截断被误标已读。（覆盖 F30、N3、N10）

### 审批与成员状态

- AC26：需要审批的成员开始任务前会发送绑定成员、任务和计划版本的结构化请求并进入等待审批；在未获有效批准时，写文件、修改仓库或执行其他副作用操作被能力边界拒绝。（覆盖 F31）
- AC27：Lead 只能用规范化结构化决定批准或驳回计划。成员、任务或版本任一不匹配的决定不生效；批准后改变计划会使批准失效并回到等待审批，驳回原因可供成员修订并提交递增的新版本。（覆盖 F32、F33）
- AC28：计划批准后，对应成员仍需通过现有工具权限、沙箱和用户高风险审批；团队批准不能授予原本不可用的能力。请求、批准、驳回、失效和重申在 CLI 重启后保持真实状态并可审计。（覆盖 F33、F34）
- AC29：成员自然完成工作时，任务获得完成状态和最终工作记录，Lead 收到任务状态通知，成员变为空闲；失败、取消或阻塞会记录相应状态与原因，而不会触发完成路径或错误地允许依赖任务开始。（覆盖 F36）

### 编排与原子集成

- AC30：给定包含并行分支和前后依赖的任务图，Lead 能创建、指派并启动全部就绪任务；无依赖的成员并行工作，后继任务在全部依赖完成前保持阻塞，并在条件满足后变为可开始。（覆盖 F35）
- AC31：存在未完成任务、未满足集成前置条件或成员工作区无法识别待集成成果时，Lead 不能启动集成；条件满足后，临时集成按任务依赖拓扑顺序纳入每个成员尚未集成的成果。（覆盖 F37）
- AC32：集成多个无冲突成果时，系统从原 Lead 基线创建临时集成分支，合入全部成果并运行约定验证；只有全部成功后才一次推进 Lead 分支。验证期间观察到原 Lead 分支未被逐步改写。（覆盖 F38、N15）
- AC33：制造合并冲突后，Lead 只能读取诊断并将修复任务派给成员，不能直接编辑冲突源码；成员修复后可重新集成。若冲突或验证失败仍无法解决，临时集成被中止和丢弃，原 Lead 分支提交保持不变，并向用户报告冲突或验证证据。（覆盖 F39）
- AC34：成功集成记录包含所纳入成员成果、验证结果和新基线，相关成员分支随后安全同步；重复提交同一集成请求不会再次纳入相同成果。失败集成不产生已纳入标记，也不删除成员原分支或原始提交。（覆盖 F40、N3、N15）

### Coordinator、安全与兼容性

- AC35：仅开启配置能力开关、仅设置环境变量或两者都关闭时，coordinator 均不生效并明确说明缺失条件；两把锁同时开启时才生效。模型消息和团队成员都不能自行改变该判定。（覆盖 F41）
- AC36：coordinator 生效后，Lead 工具清单不含文件创建、修改、删除或移动能力，但仍可读取、管理团队、终止成员、发送消息和启动集成；直接请求已移除的写工具无法执行且产生审计。（覆盖 F42、F44）
- AC37：coordinator 的 shell 能执行只读检查、受控验证和必要 Git 集成操作，但使用写文件命令、重定向、管道写入、脚本解释器、子进程、Git 外部驱动或等价绕过方式修改源码时均在执行前被拒绝；暂存和提交仅能作用于受控临时集成结果。（覆盖 F43、N16）
- AC38：coordinator 遇到需要修改源码或冲突文件的事项时，会创建或更新共享任务并委派成员；模式启用、禁用原因和被拒绝的写入均有可关联且不含敏感参数的审计记录。（覆盖 F44、N13）
- AC39：团队名、成员名和持久化内容针对绝对路径、`..`、分隔符、符号链接跳转和名称碰撞的测试均无法逃逸团队或 worktree 边界；审计、诊断和成员上下文不包含 API 密钥、临时授权或完整敏感工具参数。（覆盖 N4、N6）
- AC40：达到配置或硬上限的成员数、任务数、依赖数、消息大小、摘要大小、广播规模和上下文积压会得到有界错误或安全摘要；成员并发、恢复、停止、唤醒和 Git 操作均不会无限占用线程、窗格、内存、磁盘或等待时间。（覆盖 N9、N10、N11）
- AC41：模拟团队文件损坏、版本不兼容、成员异常、邮箱失败、审计失败和 Git 失败时，系统停止受影响操作、保持关键原状态并给出定位信息，不猜测审批或已读状态；其他团队、成员与普通会话继续运行。（覆盖 N12、N14）
- AC42：普通对话、一次性子 Agent、后台任务、Skills、Hooks、MCP、权限、会话恢复、上下文管理、Plan/Do 模式、命令路由和现有 worktree 测试全部回归通过；项目在声明的 Python 3.10 及以上版本通过团队功能的确定性单元与集成测试。（覆盖 N18、N19）
- AC43：用户可见输出能用团队、成员、任务、消息、计划版本、后端和集成 ID 关联操作与错误，且在不读取内部持久化文件的情况下判断任务为何阻塞、成员为何降级、审批是否有效以及集成是否推进。（覆盖 N20）

### 端到端场景

- AC44：用户在 Git 工作区创建团队，添加一个强隔离成员和一个自动降级为轻量后端的成员，将含依赖的任务分别指派给两人；两者在独立 worktree 中按就绪状态并行或等待，通过点对点消息直接协作，任务完成后通知 Lead 并进入空闲，普通一次性子 Agent 始终看不到团队工具。
- AC45：需要审批的成员提交计划版本一并被 Lead 驳回，修订为版本二后获得结构化批准；成员仍经过现有权限检查完成任务。CLI 退出并重启后，成员从同一身份和上下文恢复，先处理停机期间邮箱消息，再接受下一项任务。
- AC46：两个成员提交无冲突成果后，Lead 在临时集成分支按依赖顺序合并并验证，Lead 分支仅在全部成功后推进，成员长期分支同步到新基线；随后制造无法修复的冲突，重试失败后原 Lead 分支不变且成员成果仍可追溯。
- AC47：两把 coordinator 锁同时开启后，Lead 能拆任务、发消息、终止成员、检查差异和执行受控集成，但所有直接或间接源码写入路径均失败；Lead 将冲突修复委派成员，成功集成后在团队无运行任务、待审批或未合并工作时完成保护性归档并保留只读审计。
